首次交付 16 集，之后的三个场景分别交付 0、2、2 集。同一 V2Fly 来源只有 `openai`、`anthropic` 换版；多来源只有 `gfw`、`onedrive` 换版。两版核对了逐集当前交付和成功输入的完整来源、稳定 JSON/SRS 的 SHA-256、发布时间、已变与未变规则的版本沿用关系。每轮按该轮的候选与交付记录核对版本关系，跨版本对照使用来源、文件摘要和发布时间。

全部未变时，完整校验读取 16 份交付记录和 32 个产物，共 48 次。计入逐集与候选字节比对后，整次同步共读取稳定路径 96 次。两集变化时，每次实际稳定交付都会产生新提交，需要重新校验。首次交付过程中稳定分支前进 16 次，能复用同一提交的机会较少。

## 后续并行研究

这次改动减少了稳定文件的逻辑读取与重复摘要计算。四个场景的总耗时中位数变化介于 +1.3% 至 +2.2%。基线与复测分批执行，墙钟也受本机负载影响。复测第三轮未变场景为 1.584 秒，同一 V2Fly 来源变化为 3.593 秒，均计入原始数据。当前数据支持保留串行交付。当前本地未变场景约 1.33 秒用于 16 次 sing-box 工具身份检查；若继续优化，先测这部分在保留工具替换检测的前提下能节省多少时间。取源及原生构建并行可等实际瓶颈明确后再评估。内存 Git、上游响应和产物读回均在本地，GitHub 的网络成本和传输并行收益仍待单独测量。
