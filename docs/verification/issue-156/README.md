首次交付 16 集，之后的三个场景分别交付 0、2、2 集。同一 V2Fly 来源只有 `openai`、`anthropic` 换版；多来源只有 `gfw`、`onedrive` 换版。两版核对了逐集当前交付和成功输入的完整来源、稳定 JSON/SRS 的 SHA-256、发布时间、已变与未变规则的版本沿用关系。随机生成的操作 ID、候选 ID 和 Git 提交号在每轮各自的仓库内核对。

全部未变时，只需读取一次 16 份交付记录和 32 个产物；两集变化时，每次实际稳定交付都会产生新提交，需要重新校验。首次交付过程中稳定分支前进 16 次，能复用同一提交的机会较少。

## 后续并行研究

这次改动减少了稳定文件的逻辑读取与重复摘要计算。四个场景的总耗时中位数变化均在 17 ms 以内，五轮样本支持保留串行交付。当前本地未变场景约 1.29 秒用于 16 次 sing-box 工具身份检查；若继续优化，先测这部分在保留工具替换检测的前提下能节省多少时间。取源及原生构建并行可等实际瓶颈明确后再评估。内存 Git、上游响应和产物读回均在本地，GitHub 的网络成本和传输并行收益仍待单独测量。
